# Autonomous Development Setup Guide for Claude Code

## Overview

This guide provides a minimal, proven approach for autonomous Claude Code development using the Obra Superpowers skills (writing-plans and executing-plans). It combines Anthropic's internal best practices with community-tested patterns.

## Core Philosophy

**Three Principles:**
1. **One feature at a time** - Prevents scope creep and context loss
2. **Plan before execute** - Separate thoughtful planning from mechanical execution  
3. **Test-driven progression** - Always validate before moving forward

**Two-Phase Workflow:**
- **Phase 1: Planning** (Human-in-loop) - Review and approve detailed plans
- **Phase 2: Execution** (Fully autonomous) - Claude executes approved plans

## Autonomous Workflow (Obra-Enhanced)

### Workflow Modes

**Mode 1: Feature → Plan → Execute (Recommended)**
```bash
/plan-feature "User authentication with JWT"  # Creates detailed plan
# Review the plan in plans/active/
/execute-next                                 # Executes the plan
```

**Mode 2: Batch Planning + Autonomous Execution**
```bash
/batch-plan    # Creates plans for all features in features.txt
# Review all plans
/work          # Executes plans one by one autonomously
```

**Mode 3: Template-Based (For Repetitive Tasks)**
```bash
/plan-from-template [template-name]
# Fills in variables and executes
```

### Before Starting Any Feature
```bash
# Run the test suite to ensure baseline works
npm test        # or: pytest
npm run lint    # or: ruff check .

# If tests fail, fix them BEFORE implementing new features
```

### Implementation Pattern (When Executing Plans)
1. Read plan from plans/active/
2. Execute each step with validation
3. Run tests after each step
4. Commit on successful steps (conventional commit format)
5. Update progress.txt continuously
6. Move to plans/completed/ when done
7. Update features.txt to mark complete

### Commit Message Format
```
feat: add user authentication
fix: resolve token expiration bug
test: add coverage for edge cases
refactor: simplify auth middleware
docs: update API documentation
```

## Integration with Obra Skills

### writing-plans skill:
- Reads feature from features.txt
- Analyzes codebase structure
- Identifies dependencies and prerequisites
- Creates step-by-step implementation plan
- Estimates test coverage needs
- Plans commit strategy
- Outputs to plans/active/[feature-name].md

### executing-plans skill:
- Reads plan from plans/active/
- Executes each step with validation
- Runs tests after each step
- Auto-commits on successful steps
- Updates progress.txt
- Moves plan to plans/completed/ when done
- Flags blockers for human review

## Stop Conditions (Ask Human)

Claude should stop autonomous execution and ask for guidance when:

- Test coverage drops below 75%
- Breaking API changes needed
- Security implications discovered
- 3 consecutive test failures on same step
- Architectural decisions required
- Ambiguous requirements encountered
- External dependencies unavailable
- Scope significantly larger than expected

## Slash Commands

### `/plan-feature` - Create Plan for Single Feature

```markdown
# Plan Feature Command

Read the next incomplete feature from features.txt and use the **writing-plans** skill to create a detailed implementation plan.

**Process:**
1. Read features.txt
2. Identify next incomplete feature under "Todo"
3. Use writing-plans skill with that feature
4. Save plan to plans/active/[feature-slug].md
5. Link plan to feature in features.txt
6. Summarize plan for human review

**Output Example:**
"Created plan: plans/active/user-auth-jwt.md

Plan Summary:
- 7 implementation steps
- Estimated time: 2-3 hours
- Dependencies: jsonwebtoken, bcrypt
- Tests required: 8 new test cases
- Commits planned: 7 incremental commits

Review the plan at plans/active/user-auth-jwt.md
Run /execute-next when ready to proceed."
```

### `/execute-next` - Execute Next Plan

```markdown
# Execute Next Command

Execute the next plan in plans/active/ using the **executing-plans** skill.

**Process:**
1. List plans in plans/active/
2. Select highest priority (or oldest if no priority set)
3. Use executing-plans skill on that plan
4. Follow plan step-by-step:
   - Execute step
   - Run tests
   - Commit if successful
   - Update progress.txt
   - Continue to next step
5. When complete:
   - Move plan to plans/completed/
   - Update features.txt
   - Append summary to progress.txt

**Autonomous Execution Rules:**
- Run tests after each step
- Commit after successful steps only
- Stop and flag if step fails 3 times
- Update progress.txt after each step
- Ask human if stop condition encountered
```

### `/batch-plan` - Plan All Features

```markdown
# Batch Plan Command

Create plans for all incomplete features in features.txt.

**Process:**
1. Read all "Todo" features from features.txt
2. For each feature:
   - Use writing-plans skill
   - Save to plans/active/[feature-slug].md
   - Add plan reference to features.txt
3. Analyze dependencies between plans
4. Sort plans by dependency order
5. Provide execution roadmap

**Output Example:**
"Created 5 plans:

1. ✓ plans/active/database-schema.md (no dependencies)
2. ✓ plans/active/user-model.md (depends on #1)
3. ✓ plans/active/user-auth.md (depends on #2)
4. ✓ plans/active/api-endpoints.md (depends on #3)
5. ✓ plans/active/integration-tests.md (depends on #4)

Suggested execution order follows dependency chain.
Review all plans, then run /work to begin autonomous execution."
```

### `/work` - Main Autonomous Work Command

```markdown
# Work Command (Obra-Enhanced)

Start autonomous work session with plan-based execution.

**Process:**
1. Check git status - ensure clean working directory
2. Read progress.txt to understand previous work
3. Run test suite to verify baseline state
4. If tests fail:
   - Fix failures before proceeding
   - Update progress.txt with fixes
5. Check for existing plans in plans/active/
6. If plans exist:
   - Use /execute-next
   - Continue until all plans complete or blocker encountered
7. If no plans exist:
   - Read next feature from features.txt
   - Use /plan-feature to create plan
   - Ask: "Plan created. Execute now? (yes/no)"
   - If yes: Use /execute-next
8. Repeat until:
   - All features completed, OR
   - Blocker encountered (stop condition met), OR
   - All plans executed

**Fully Autonomous Mode:**
To skip confirmations between plans, add to CLAUDE.md:
```
AUTO_EXECUTE=true
```

**Session Management:**
- Continuously update progress.txt
- Commit after each successful step
- Leave codebase in working state
- Provide summary when stopping
```

- $ENDPOINT_NAME: Name of the endpoint (e.g., "user", "product")

- $AUTH_REQUIRED: Whether authentication is required (true/false)

- [ ] Database schema exists for $ENDPOINT_NAME
- [ ] Authentication middleware available (if $AUTH_REQUIRED=true)
- [ ] Validation schemas defined

**Action:** Create route handler for $ENDPOINT_NAME
**Files to create:** src/routes/$ENDPOINT_NAME.ts
**Validation:** Route module exports correctly
**Commit:** feat(api): add $ENDPOINT_NAME route handler

### Step 2: Implement GET Method
**Action:** Implement GET /$ENDPOINT_NAME
**Files to modify:** src/routes/$ENDPOINT_NAME.ts
**Tests required:** tests/routes/$ENDPOINT_NAME.test.ts (GET cases)
**Validation:** 
- Returns 200 with valid data
- Returns 404 for non-existent resources
- Handles query parameters correctly
**Commit:** feat(api): implement GET /$ENDPOINT_NAME

### Step 3: Implement POST Method
**Action:** Implement POST /$ENDPOINT_NAME
**Files to modify:** src/routes/$ENDPOINT_NAME.ts
**Tests required:** tests/routes/$ENDPOINT_NAME.test.ts (POST cases)
**Validation:**
- Returns 201 on successful creation
- Returns 400 for invalid input
- Returns 409 for duplicates
**Commit:** feat(api): implement POST /$ENDPOINT_NAME

### Step 4: Add Authentication (if required)
**Condition:** Only if $AUTH_REQUIRED=true
**Action:** Add auth middleware to protected routes
**Files to modify:** src/routes/$ENDPOINT_NAME.ts
**Tests required:** tests/routes/$ENDPOINT_NAME.test.ts (auth cases)
**Validation:**
- Returns 401 for missing token
- Returns 403 for invalid token
**Commit:** feat(api): add authentication to $ENDPOINT_NAME

### Step 5: Add Input Validation
**Action:** Add request validation middleware
**Files to modify:** src/routes/$ENDPOINT_NAME.ts
**Files to create:** src/validators/$ENDPOINT_NAME.ts
**Tests required:** tests/validators/$ENDPOINT_NAME.test.ts
**Validation:** Invalid requests return 400 with clear error messages
**Commit:** feat(api): add input validation for $ENDPOINT_NAME

### Step 6: Update API Documentation
**Action:** Add endpoint to API docs
**Files to modify:** docs/api.md or swagger.yaml
**Validation:** Documentation renders correctly

## Key Advantages

### 1. **Separation of Concerns**
- **Planning:** Thoughtful, strategic, reviewed by humans
- **Execution:** Mechanical, systematic, validated by tests

### 2. **Human Review at Right Time**
- Review plans before execution (prevent wasted work)
- Review code after execution (verify quality)
- Not: Interrupt during execution (breaks flow)

### 3. **Resumable & Persistent**
- Plans persist across sessions
- Progress tracked continuously  
- Can pause/resume anytime
- Context never lost

### 4. **Template Reuse**
- Create templates for common patterns
- Consistency across similar features
- Faster planning for repetitive work

### 5. **Progressive Refinement**
- High-level features → Detailed plans → Execution steps
- Expand detail as execution reveals needs
- Adapt without losing structure

### 6. **Clear Audit Trail**
```
Feature (features.txt)
  ↓
Plan (plans/active/*.md)
  ↓
Execution Steps (progress.txt)
  ↓
Commits (git log)
  ↓
Completed Plan (plans/completed/*.md)
```

## Best Practices

### Do's ✓
- Review plans before execution
- Keep features in features.txt high-level
- Let writing-plans create detailed steps
- Commit after each successful step
- Update progress.txt continuously
- Run tests frequently
- Leave code in working state

### Don'ts ✗
- Don't mix planning and execution
- Don't skip plan review
- Don't work on multiple features simultaneously
- Don't commit broken code
- Don't ignore test failures
- Don't proceed without baseline tests passing

## Troubleshooting

### "Plans are too detailed"
→ Keep features.txt high-level, let AI add detail

### "Plans are too vague"
→ Add project-specific examples to CLAUDE.md

### "Execution gets stuck"
→ Check stop conditions, may need human input

### "Tests keep failing"
→ Review test strategy in plan, may need refinement

### "Too many commits"
→ Adjust commit granularity in CLAUDE.md

### "Lost track of progress"
→ Check progress.txt and git log
